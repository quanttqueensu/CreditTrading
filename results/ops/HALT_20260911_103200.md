# INCIDENT — the 2026-09-10 CEF session ran for 17h20m and every guard read green

Detected: 2026-09-11 10:32 ET   Detected by: a state check before a promotion, not by any alarm
First occurrence: 2026-09-10 17:15:05 ET   Sessions affected: 1 (cef, asof 2026-09-10)

**No halt was written and none is needed: the session finished, armed, and exited
0 at 10:38:32.** This is a written record of a fault that did not stop the book
but hid from everything built to see it. `[V]` verified by re-running the command
shown, `[S]` sourced not re-read.

## What happened

| when | what |
|---|---|
| 09-10 17:15:05 | session starts, `deadline 23:30, poll every 900s` |
| 17:15 → 19:45 | polls every 15 min. **yfinance NAV 0/17, CEFConnect NAV 0/17** on every one |
| 19:45 → 21:27 | one poll in 1h42m — the machine is sleeping between wakeups |
| 21:27 | last poll of the day. Still 0/17 on both sources |
| **23:30** | **the deadline passes with the process asleep. Nothing fires** |
| 09-11 09:46:26 | wakes, finds **NAV 17/17 and close 17/17 dated 2026-09-10**, returns 0 |
| 09:46:33 | refreshes panels → prices and NAV to 2026-09-10 |
| 09:46 → 10:38 | **hung ~52 min in `fetch_borrow_rates.py`** |
| 10:38:29 | `panel scripts/cef/fetch_borrow_rates.py FAILED rc=1 (session continues)` |
| 10:38:30 | preflight all PASS, **ARMED**, `asof=2026-09-10` |
| 10:38:32 | `done status=ok` |

88099  0.0 %CPU  S  17:21:22 elapsed   /opt/anaconda3/bin/python3 .../launch_job.py cef

## What it cost

**Nothing irrecoverable, and that is luck rather than design.**

- **No orders were lost.** It had not armed while hung, so nothing was
  transmitted during the 17 hours. When it did arm it placed the 2026-09-10
  decision, which under this book's `shift(2)` convention fills at **2026-09-11's
  close** — the same auction the order would have reached had the session
  finished on time the previous evening. The economics are unchanged; only the
  delivery was late.
- **`arm()` did its job.** It adopted broker truth on four names — JFR
  −5,837→−10,467, MHD −8,856→−8,741, NEA −7,118→−11,576, MQY −1,750→−1,565 —
  i.e. the 09-09 MOC orders had filled at 09-10's close and the ledger had not
  noticed. `[V]`
- **The borrow panel was not refreshed.** `IBKR API FEE_RATE -- 0/17 names; no
  fee rate from either source; not writing a row`. `data/cef/cef_borrow.csv`
  still ends 2026-09-10. Non-fatal by design, and correctly non-fatal.
- **It blocked other work for 17 hours**: the promotion (correctly — a live pid
  is exactly what must stop a checkout) and the `cef_distributions` refresh
  (correctly — that panel is on the live path).

## Root cause

Three faults in series. Only the first is about the market.

**1. NAV was genuinely unavailable on 2026-09-10.** Both sources, all evening,
all 17 names. Not our bug.

**2. The deadline bounds the WAIT, not the SESSION — and the machine slept
through it anyway.** `scripts/cef/wait_for_nav.py` checks completeness *before*
the deadline, deliberately (its own docstring says so). So a poll that sleeps
past 23:30 and wakes at 09:46 to find the data takes the success path and returns
0. There is no clock anywhere that says *this decision is too old to act on*.
`com.quantt.awake` holds the machine up 09:00–20:00 on weekdays while the session
polls to 23:30, so the last 3.5 hours of every evening are outside the awake
window — `ops/doctor.py`'s `sleep` check already warns about exactly this and the
warning has been standing. `[V]`

**3. `fetch_borrow_rates.py` has no overall timeout.** It spent ~52 minutes
getting `FEE_RATE 0/17` before giving up. `ib.connect(..., timeout=20)` and
`reqHistoricalData(..., timeout=30)` bound individual calls; nothing bounds the
loop over 17 names × 2 sources.

## Why nothing caught it

Each guard was answering a question that happens to have the same answer for
"running" and "hung".

- **`check_launchd`** reads `launchctl list` and sees a pid. A hung session has a
  pid.
- **`run_watchdog`** compares heartbeat **dates**. An unfinished session has
  written no heartbeat, so cef's last beat stayed 2026-09-09, and the arithmetic
  is `missed = len(bdate_range(last, today)) - 1; if missed > 1`. On the evening
  it broke, `missed` was **1**. Not greater than 1. All clear. `[V]` It would not
  have flagged until this evening's 19:30 run — **48 hours after the fault
  started.**
- **`ops/doctor.py`** had no concept of a session that is running too long.
- **The heartbeat itself** is written at the *end* of a session, so the one
  artefact that would have said "this is not finished" is the one a stuck session
  cannot produce.

**The pattern is the one this repo keeps writing down: a guard that shares an
assumption with the thing it guards is not a guard.** Every check here assumed a
session either finishes or never starts.

## The guard that would have caught it

`ops/doctor.py::check_stuck_sessions`, added with this record.

For each of `cef`, `phase0`, `benchmarks`, if `launchctl list` reports a live
pid, it takes the process age from `ps -o etime=` and compares it against a
ceiling **derived, not written down**: `cef.env`'s `NAV_DEADLINE` minus the
plist's `StartCalendarInterval`, plus an hour of slack for the trade and capture
phases. For cef that is 23:30 − 17:15 + 1h = **7h15m**. An unparseable deadline
WARNs and skips rather than guessing a ceiling — the defect class here is a
literal that stopped matching reality, and a default would rebuild it.

It is a **FAIL**, unlike the backup job's WARN, because a stuck session does stop
the book: it holds the session slot and the next run may collide with it.

**It runs outside the thing it guards**, which is the property that matters:
`ops/doctor.py` is called by `run_watchdog` through `doctor.failures()`, and the
watchdog is a separate launchd job. Against the measured incident it reports:

```
[FAIL] stuck:cef  pid 88099 has been running 17h17m, past its 7h15m ceiling.
                  It cannot still be doing useful work, it holds the session
                  slot, and the next run may collide with it
   fix: check the tail of ops/schedule/logs/cef_*.log, then
        launchctl kill TERM gui/$(id -u)/com.quantt.cef.daily
```

`ops/tests/test_stuck_session_guard.py` pins that case, and pins that an ordinary
4h45m evening poll is a PASS — a guard that interrupts the book every normal
night would be worse than none.

## Resolution

- Guard added and tested. **This is in DEV.** `~/prod/QUANTT` is detached at
  `v2026.09.10.1` and has none of it; the watchdog will not run this check until
  a promotion carries it.
- The session was **not** killed. Terminating it was attempted and refused by the
  harness; it then completed on its own at 10:38:32 and the point became moot.
- `data/cef/cef_distributions.parquet` refreshed at 10:48, once no session was
  running: 2026-07-24 → **2026-09-10**, all 17 deployed names current.

## Deliberately NOT changed

- **`wait_for_nav`'s completeness-before-deadline order.** It is correct for what
  it does, and the incident is not that it waited — it is that nothing bounded
  the session around it. Changing that ordering would trade a rare late session
  for routinely missed ones.
- **`fetch_borrow_rates`'s missing overall timeout.** Real, and the right fix is
  a bounded loop, but it is a panel script off the live path and the new guard
  now catches the symptom. Worth doing; not worth doing in the same change as the
  guard.
- **The `com.quantt.awake` window.** Extending it to cover 23:30 is a `sudo
  pmset` change that doctor already recommends, and it is the operator's call.

## Open

- The **48-hour watchdog latency** is untouched. `missed > 1` means a single
  missed session is never reported. The stuck-session check closes the *hung*
  case; a session that simply never fires is still two days invisible.
- **FCT** returned no distribution history on this refresh (`empty: ['FCT']`) and
  its whole series left the panel — 43 tickers where there were 44. It is not one
  of the 17 deployed names and its NAV has been stale since 2026-08-06, so it
  looks delisted or merged. `data/cef/cef_universe.csv` still lists it. There is
  no older copy: `data/` is gitignored and `backup_state.sh` deliberately
  excludes the parquets.
